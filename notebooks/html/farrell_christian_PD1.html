TODO — Project recap¶

Project title:
Adaptive Defense Evaluation with Security-Utility Tradeoffs

Research question:
Under a fixed attack budget, how much does the security of language model erode when an attacker can observe a defense and adapt their attacks, and how does this anticipation affect benign requests and false refusals?

What is the input to the system or experiment?
A set of harmful prompts and their corresponding attack method, and a set of benign and their corresponding request category.

What is the output or behavior you will measure?
The target language model’s response to each attack, as well as if it was successful or not. Also recording whether or not benign prompts had been unnecessarily refused and why.

What is the main comparison you expect to make?
A defensive model evaluated against both static attacks and an adaptive attacker that can use the defense’s previous responses to modify subsequent attacks.

What changed, if anything, since Deliverable 0?
I addressed a number of things based on feedback recieved on Deliverable 0.

Seperated and Identified Components

Prompt set identifed: HarmBench + XSTest.

Attack family identified: random-search suffix (Andriushchenko et al., ICLR 2025).

Defense identified: safety system prompt (one defense for this checkpoint).

Target model identified: Qwen2.5-1.5B-Instruct.

Evaluator identified: a refusal-string rule for now.

Static vs Adaptive Defined

Static = suffix optimized against the undefended model, then replayed against the defended model.

Adaptive = suffix optimized against the defended pipeline.

Attacker Budget Defined

One query = one forward pass of the full target pipeline (defense included) on one candidate prompt. Every condition gets the same budget.

Scope: one model, one attack family, one defense for this checkpoint. The second attack family (an LLM attacker that reads refusals) and more defenses wait for Deliverable 2.

Added a direct utility measure 10 exact-match questions like simple math problems beyond false-refusal rate.

14. Feasibility verdict¶

Use the following decision rule.

GREEN — feasible¶

The main resources are accessible, the core pipeline runs, the baseline works, and the estimated experiment fits the available time and hardware.

YELLOW — feasible after a change¶

The project can work, but the model, data size, number of conditions, or method must be reduced.

RED — not feasible in the current form¶

A required model/data/resource is unavailable, the compute cost is too high, the baseline cannot be reproduced, or the planned experiment depends on a component you cannot obtain.

A YELLOW result is completely acceptable if you provide a good scope correction.

Final feasibility verdict¶

Verdict: YELLOW

Evidence for the verdict:

  • What worked: The complete pipeline (Qwen2.5-1.5B-Instruct, tokenizer, chat template, pinned benchmark datasets, defense wrappers, logging, and summary metrics) runs end-to-end reliably in ~10 minutes, generating clean JSONL and CSV outputs within ~3 GB of GPU memory on a 16 GB baseline.
  • Why it is Yellow: The 50-query search budget was too small for random search to break the defense (0 of 20 searches achieved the target token, and ASR was identical at 1/10 across all arms). Furthermore, the string-matching judge has visible false positives/negatives, and scaling the full query budget across multiple models and defenses would exceed realistic compute limits without scope reduction.

Largest remaining technical risk:
Adversarial search query budget scaling: Balancing compute time per search while giving the optimizer enough iterations (e.g. 200–500 queries) to actually find working adversarial suffixes.

Largest remaining research-design risk:
Judge reliability: A simple refusal-string judge can misclassify non-refusal gibberish or pushback as jailbreak successes. A stronger LLM judge (or classifier) with human agreement checks is needed to evaluate true compliance.

Scope change you recommend now, if any:

  1. Focus on one primary model (Qwen2.5-1.5B-Instruct) and two defense setups (neutral baseline prompt vs. safety defense) rather than multiple architectures.
  2. Narrow to 30–50 curated harmful behaviors rather than 100+.
  3. Increase the query budget on a smaller set of behaviors first (e.g. 200–500 queries on 10 behaviors) to observe attack convergence before scaling.
  4. Upgrade from simple substring matching to an automated LLM/classifier judge alongside a hand-labeled validation subset.

What you will do next:
